# BBDown-rust Bilibili Migration

## Summary
- Bilibili downloads now target the `BBDown-rust` `bbdown-core` crate API instead of the legacy .NET `BBDown` argument surface or the `bbdown` CLI.
- The bot supports Bilibili season/media and intl routing, with Telegram selection prompts for `ss/md` series links.
- BBDown login management now uses direct crate APIs for Web QR, TV QR, access-key handoff, credential health, and logout.

## Current State
- Bilibili preflight uses `BiliClient::plan_download_with_mode` to resolve bvid, aid, cid, and epid identities for duplicate detection.
- Downloads use `BiliClient::download_plan_with_progress`; the bot converts the structured report into its existing NFO, staging, and duplicate-handling flow.
- `/bbdown login [web|tv|access-key]` uses direct QR/access-key APIs; access-key login is a two-step Telegram flow that waits for the callback URL or `balh-login-credentials:` message.
- `/bbdown status` reads `BiliClient::check_credential_health`; `/bbdown logout` clears the selected BBDown-rust credential/profile and removes legacy bot-managed Web cookie state.
- Config exposes structured `playurl_mode`, `restricted_area`, restricted proxy lists, credential profile, and `danmaku_formats`; known legacy flags in both `extra_args` and `global_args` are translated for endpoint/playurl/restricted/request-timeout compatibility, with new fields taking precedence, and `download_args` retains `--only` mode compatibility.
- Access-key callback tickets remain reserved while an attempt is running and are removed after credentials save successfully. Parse failures remain retryable only while the auth generation, durable epoch, ticket identity, and TTL are unchanged; a save path that advances or loses the epoch discards the stale ticket and requires a new login flow.
- Access-key callbacks carry a per-ticket identity in addition to the auth generation. An expired completion cannot clear or release a newer ticket, and in-progress tickets are not pruned underneath their completion task.
- Bilibili API and media requests use the browser-compatible `Mozilla/5.0` user agent expected by Bilibili media CDNs; application-specific user agents caused reproducible 403 responses after stream planning.
- Direct Bilibili downloads rely on `bbdown-core` request and media idle timeouts instead of the bot's external-command total timeout. The outer worker owns a process group without a total deadline; local ffmpeg inherits that group while retaining its own total and idle deadlines, and cancellation tears down the owned group. Active long downloads are no longer cancelled at the two-hour external-command boundary, stalled media reads still fail after the configured idle interval, and mux cannot outlive a terminated worker.
- Credential reads and updates use the pinned `bbdown-core` credential store transaction API. Legacy cookie migration, fresh login, and logout additionally share a permanent bot-owned cross-process mutation lock. Its fsynced epoch is stored in two alternating fixed-size, checksummed slots after the bounded legacy log area; existing append logs, including an incomplete final record or a near-limit log, migrate without further growth. The epoch is captured with the lock device/inode identity when login begins, checked before credential save, and rechecked while final status/login/logout Telegram replies hold the same lock. A pending login therefore cannot recreate credentials after another process logs out, cannot cross a retargeted ancestor path with a coincident numeric epoch, and a pre-mutation health or success result cannot be published after the lock identity changes. A new lock is fully initialized with a version header before an atomic no-replace install. Existing files must match that format or a strict legacy epoch log before permissions or contents can change. The lock is opened without following symlinks, uses an exact two-link primary/anchor pair, and persists a separate private ownership record bound to the lock device/inode before any auth mutation can run. The configured credential file resolves once to its canonical parent for the complete transaction; a direct credential-parent symlink is rejected rather than becoming a retargetable selector. A missing public alias is restored only to that anchored inode; losing both aliases after initialization fails closed instead of resetting the epoch. Replacement paths, ownership-record mismatches, and unknown hard-link aliases are rejected. No-op legacy synchronization avoids epoch changes, and concurrent access-key or TV-key changes remain protected by the core store transaction.
- `/bbdown logout` cancellation now covers QR ticket creation, Telegram ticket delivery, confirmation messages, access-key pending-state acquisition, and poll sleeps in addition to active QR polling.
- Duplicate detection walks each media-library directory once and builds one media identity index per incoming job, so Bilibili plan identities reuse filename, NFO, and info JSON reads instead of rescanning sidecars or parent directories for every candidate ID.
- Bilibili bvid/aid and filename-only cid/epid matches remain duplicate prompts but cannot authorize destructive replacement. Overwrite requires one exact cid/epid match for a single-entry plan that is proven by NFO or info JSON metadata. The move path binds the original output root with a directory descriptor, uses no-follow parent traversal and atomic no-replace renames, and tracks acquired objects by device, inode, and file type. The old media and sidecars first move into an exclusive transaction-owned backup directory, then a strict identity index is rebuilt from those acquired files; missing targets, unreadable metadata, identity changes, recreated paths, destination races, parent symlink replacement, and new ambiguity are rejected with identity-bound rollback. FLV concat mux uses a unique transaction-owned temporary list and never removes a pre-existing `ffmpeg-concat.txt`.
- Bilibili overwrite execution validates the freshly resolved download plan against the confirmed cid/epid before downloading. Overwrite cleanup acquires only basename-bound sidecars, preserves ambiguous bare Bilibili sidecars, and detects configured-root symlink retargeting for new mutations. Recovery retains parent directory bindings and validates their object identities directly, so rollback restores into the captured directory object even after a concurrent rename or root retarget. If a completed overwrite unexpectedly contains multiple primary media files, the transaction preserves the old file and commits every new output with keep-both naming instead of discarding staging.
- Overwrite confirmation retains an `O_NOFOLLOW` descriptor for the exact media object until the queued download finishes, preventing inode reuse from transferring authorization to a replacement. Backup files keep their original names under a private transaction directory with an fsynced v4 recovery manifest bound to the root, parent, and transaction directory identities; full-video commits move primary media before sidecars, fsync every committed output, create a durable same-inode hard-link anchor for each one, then publish the complete `committed` manifest by atomic file exchange before deleting backups. A destination race discovered after exchange is exchanged back while both post-exchange object identities remain provable; otherwise both names are retained without deletion. The committed manifest records the actual replacement primary filename, including an extension change. Recovery always runs at startup. Each later output-lock owner writes a persistent dirty marker before mutation and restores it to clean only after the operation and any required recovery finish safely; only a non-clean handoff triggers another recursive library recovery scan. Diagnostics from unreadable, disappearing, or replaced ordinary library subtrees remain visible but do not dirty that state, because they identify no managed recovery transaction; only a discovered quarantine, mux, staged publication, or overwrite transaction that cannot be authenticated or completed requires another pass. Recovery removes an interrupted transition file only after its private access policy, canonical encoding, transaction ownership, and opposite-phase relationship to the active manifest are authenticated. It rolls back only an authenticated, unoccupied `acquired` transaction and finalizes an authenticated `committed` transaction only while every output still matches its persisted anchor. Legacy v2/v3 transactions, copied or forged current manifests, and unrecognized transition files are retained fail-closed. Unknown legacy directories and malformed transactions are retained, while unrelated unreadable children are reported and skipped without blocking the remaining scan.
- A later review refines the ordinary-subtree rule above: a disappearing child does not leave a reachable subtree, but an unreadable or identity-replaced directory can still conceal a managed transaction. Those scan failures persist an `incomplete` recovery marker rather than clean; output locks report diagnostics and block new downloads without recursively rescanning on every job. A later complete startup recovery clears the marker.
- Staged duplicate downloads bind the configured output root and atomically install an owner-record-bearing private job directory before network transfer begins, reuse that root binding for commit, and clean only the captured staging object through descriptor-relative traversal. Bilibili runs in an internal worker whose cwd is installed from the bound staging directory with `fchdir`; YouTube subprocesses use the same bound-cwd execution path, so a configured symlink retarget cannot redirect network writers on macOS. Before the first output rename, staging persists an identity-bound publication manifest, fsyncs every source, then syncs every distinct source directory bottom-up through the staging root. Destination parents are created through bound traversal and each new component is durably linked before descent. Normal publication fsyncs each destination; startup rolls an interrupted keep-both or committed overwrite forward, rolls an acquired overwrite back before restoring old media, and removes staging only after the selected direction completes. Owned staging without a publication manifest is discarded as an incomplete download unless it carries a root/staging-identity-bound `.retained.json`; completed outputs that exceed the publication step or manifest-byte limit receive that marker and remain available for manual recovery across restarts. Unowned or mismatched data is retained. Identity metadata discovery scans actual directory entries, so mixed-case `.NFO` and `.INFO.JSON` files participate in both the initial duplicate index and overwrite revalidation on case-sensitive filesystems.
- Bilibili staging is marked for recovery before the worker starts. A normally returned worker failure explicitly discards only a confirmed unmarked incomplete staging object, while task cancellation leaves the identity-bound directory untouched. The output lock uses an exact two-link pair between the legacy root name and an anchor in the owner-record-authenticated control directory. That anchor is created and persisted inside the private candidate control directory before the complete directory is atomically published, so a crash cannot expose an owner-only control state. The worker inherits the exact held lock object and validates its identity and private access policy, so deleting or replacing the legacy name, a parent crash, or cancellation cannot let restart recovery overlap a still-running worker. Startup restores only a missing alias to the anchored inode, waits for the inherited lock, then preserves completion-marked media and discards unmarked interrupted staging after the worker lifetime has ended, without a marker-check/delete race in the task drop path.
- Internal Bilibili worker configuration first creates an empty private file, durably unlinks that exact inode through identity-bound removal, then serializes and rewinds credentials only through the still-held `0600`, zero-link descriptor before inheritance. Staging no longer copies legacy `BBDown.config`; startup recovery removes both obsolete linked request files and copied configs from owned retained jobs before preserving media for manual recovery. Proxy URL userinfo is also redacted at log and Telegram boundaries.
- Before the Bilibili worker launches, staging persists a non-sensitive, root-and-directory-identity-bound lifecycle record in the `launched` phase. Once core media download completes, the worker atomically transitions it to `core_download_completed` before it attempts the ordinary retention marker; restart recovery accepts either side of the authenticated atomic exchange as completed, but discards a launch-only lifecycle as incomplete. A generic parent-side worker error now checks that same lifecycle after a missing marker: it retries the marker and preserves only core-completed staging, while a verified launch-only lifecycle is discarded. The parent reports a distinct retention-marker failure outcome, retries the marker, and preserves the bound staging directory instead of classifying completed media as an incomplete job. A valid completed lifecycle therefore retains otherwise unmarked Bilibili staging for manual recovery without preserving partially downloaded jobs. Each local mux transaction now validates, removes raw inputs, finalizes its recovery directory, and releases its bound descriptors before the next entry begins.
- An overwrite commit error after publication marks the bound staging job for recovery instead of allowing its drop guard to delete the publication manifest. Incomplete move rollback is carried as a typed error state and likewise preserves staging without retiring an acquired overwrite transaction. Startup therefore rolls back failures that retained the acquired overwrite phase and rolls forward failures after committed-manifest publication. If staging recovery remains unresolved after a partial step, its exact path/device/inode-bound overwrite references are deferred from the same recovery pass and resume only after staging reaches a terminal state. Output traversal also fsyncs each containing directory immediately after implicitly creating a nested destination component, before relying on that component for deeper publication.
- Progress delivery uses a latest-value channel and sends at `bot.progress_update_seconds`; bursty `bbdown-core` events are coalesced instead of accumulating unbounded Telegram requests. Pending duplicate decisions are capped against the process descriptor limit and swept on a timer, so unanswered prompts release their retained media descriptors without requiring another Telegram event.
- Credential path validation rejects the legacy state file, both legacy config filenames, every path under the stale-config directory, and existing hard-link aliases that legacy logout cleanup could remove. Missing paths resolve existing ancestors before normalizing remaining parent components, preserving filesystem symlink semantics during alias detection; case-only path separation is rejected conservatively, and macOS path components also compare in decomposed Unicode form. Legacy logout cleanup rechecks device and inode immediately before every removal and refuses to unlink any path that resolves to the active credential object.
- Config validation also rejects a legacy auth state whose leaf entry is a symbolic link. Logout clears the selected `bbdown-core` credentials only after every migratable legacy state and config path is removed successfully, so a cleanup failure or post-validation namespace replacement cannot leave an old cookie able to recreate a cleared login.
- Config validation and every state-aware auth entry point reject a legacy auth-state path that crosses a symbolic-link ancestor before any lock, read, import, or cleanup operation. Root-owned macOS system aliases are accepted as platform path roots; configurable symlinked parents are never accepted as state selectors.
- Legacy state and stale-config cleanup now binds both the selected target and initial credential objects, atomically quarantines only that target identity through no-follow parent descriptors, and rebinds the active credential path before unlink. The stale-config directory itself must be a current-user-owned `0700` non-symlink; cleanup reads it through the bound directory descriptor and can remove only recognized bot-generated `cookie.config.*.tmp` and `probe.config.*.tmp` files. A namespace swap to the selected target rejects cleanup and restores the quarantined name; an unreadable or unverifiable credential path fails closed instead of being treated as missing.
- Auth startup and every state-aware credential transaction reconcile crash-interrupted legacy cleanup while holding the permanent cross-process auth lock. Versioned manifests persist the exact original leaf and whether restoration requires current credential revalidation. Recovery scans managed entries only in the direct state/config parent and the exact bound stale-config directory, revalidating the latter's private access policy before and after descriptor-bound recovery; a symlinked or permission-widened stale-config directory blocks authentication without scanning its target. It deletes the selected object only when its device/inode differs from the freshly rebound credential, restores it when they match, advances the durable auth epoch after successful cleanup, and blocks startup or authentication if restoration or any unresolved managed state proves the configured paths unsafe. Previous deletion-only manifests and tombstones remain recoverable; v1/v2 quarantine cleanup emits a v2 terminal tombstone rather than an invalid partial v3 record.
- `/bbdown status` and login-success replies recheck both a stable even auth generation and the exact credential revision while serializing Telegram replies. Login and logout advance the revision after credential mutation, so an older health or success result cannot appear after the newer operation. Default-profile logout resolves and removes the selected profile inside one credential-store transaction, and a fresh login stops before replacing credentials if legacy migration fails or the legacy state is malformed or unreadable.
- Local Bilibili mux binds every raw input and a read-write output object inside a private `0700` staging directory, then gives ffmpeg inherited descriptors for those exact objects. Raw inputs and FLV concat data use inherited read descriptors; output uses ffmpeg's seek-capable `fd` protocol with an explicit MP4 format, so ffmpeg never reopens a writable lexical path or truncates a substituted leaf or ancestor. The public final path remains absent until that exact nonempty output object and its original transaction access path are revalidated, fsynced, and atomically published with no-replace semantics. Completion accepts only that same output identity, and raw inputs are removed only while all bound output paths and each exact input object remain stable. Identity-bound removal first creates and fsyncs an ownership manifest, atomically quarantines the selected object, validates device/inode/type, and unlinks only the matching object; a racing replacement is restored or retained. Dirty output-lock acquisition recursively reconciles a crash-retained valid quarantine by completing its intended deletion and retains unrecognized or mismatched quarantine data for manual inspection.
- Mux publication now persists a transaction manifest before ffmpeg starts, sets the held output inode to public-readable `0644`, and creates a same-inode output anchor before raw-input cleanup. Every raw removal revalidates all output paths and anchors; the manifest and anchors remain together until the final validation, then the complete transaction directory moves atomically into a recursive removal quarantine. Startup recovery discards verified unpublished partial mux output, restores a missing published path from its anchor, resumes identity-bound raw cleanup, and retains a transaction when an unrelated replacement occupies the output path. Overwrite transaction teardown uses the same durable whole-directory protocol instead of deleting committed anchors individually. Removal quarantines publish a parent-directory tombstone before deleting their internal manifest or directory, so both partial teardown windows are restart-recoverable; ordinary suffix-matching JSON files are not classified as tombstones. Recovery state uses exact-length atomic replacement inside an owner-record-bound private control directory that is itself fully initialized before an atomic no-replace install; the legacy root marker remains read-only and triggers one migration recovery scan.
- All command progress, replay diagnostics, worker error chains, Telegram edits, standard messages, and photo captions pass through one BBDown/Bilibili credential redactor before logging or delivery. Only the explicit access-key authorization message bypasses payload redaction, while its log record remains redacted.
- The privileged `pull_request_target` Codex review gate invokes `JoeyTeng/codex-review-gate-action` through the reviewed immutable `v1.2.1` commit SHA rather than a mutable major-version tag.
- Command progress reconstructs stdout and stderr into complete logical records before parsing or logging them. Sensitive JSON, cookies, authorization headers, proxy userinfo, and multiline credential values are redacted even when arbitrary pipe reads split their marker or value; normal command completion drains queued chunks and flushes the final unterminated record.
- A fully rolled-back staged publication durably retires its identity-bound publication manifest before restoring and deleting the acquired overwrite transaction. The completed replacement remains retained for manual recovery, while restart recovery sees the restored original and no longer misclassifies the absent overwrite transaction as a roll-forward instruction.
- The migration implementation and Rust validation are complete. Live Telegram login and selection flows were exercised during development; a full post-fix long-video completion remains an operational smoke test after deployment.
